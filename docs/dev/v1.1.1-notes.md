# 1.1.1 实现记录：两套部署互不干扰

对应版本：`manifest.json` `1.1.1`（`minAppVersion` 仍是 `1.1.0-beta`）。
1.1.1 是一次补丁发布，主题只有一个：**同一台机器上跑两套 Strata 时，它们不许互相
看见、互相写、互相搬文件。** 另外附带两个小修（停机也能更新、瘦卡能切环境）。

旧文档不动：1.1.0 的三批记录仍在 `v1.1-docker-notes.md`、`v1.1-firstrun-notes.md`、
`v1.1-layering-notes.md`，本文只覆盖 1.1.1 新增的判断。

## 1. 问题的形状

四件事看起来分散，根子是同一条：**Strata 自己按「用户」记账，而本 App 的模型是「配置」。**

| 谁在记账 | 记的是什么 | 两套部署同时存在时 |
|---|---|---|
| `setup.py` 的 `settings.json`（按用户一份） | 上次用过的 `data_dir`、跑过 setup 的 `installs` 列表 | 谁最后跑谁拥有，另一套下次运行会把前一套的模型文件「迁移」到自己目录 |
| App 的 profile | `strataDir`、`ggufDir`、端口… | 以前没有 `dataDir`，于是 setup 往哪写只能听 `settings.json` 的 |
| `pgrep -f serve/server.py` | 机器上所有 Strata 服务进程 | 停着的配置显示「启动中」，启动返回 `already: true`，停止会杀掉隔壁的 pid |

三者叠加的实际后果：给第二套跑 setup，第一套的 `packs` / `mtp` 被搬走（真实发生过
两次）；两套同时在线时，面板的状态、启动按钮、停止按钮全部指错对象。

## 2. `dataDir` 变成配置的必填属性

- **位置**：`profile.dataDir`，与 `strataDir` 同级，本机配置必填。
- **没有默认值、没有兜底。** `missingProfileFields()` 对 local 返回
  `["strataDir", "dataDir"]` 里缺的那些；`profileReady()` 因此为 false，
  `GET /profiles` 把它带出去，面板列成「缺失字段」，`setup.py` 干脆不跑
  （`lib/firstrun.js`：`这套配置还没有数据目录（dataDir）：请在配置里补上再运行 setup`）。
  这条是刻意的：猜一个路径比拒绝运行危险得多，猜错就是把别人的数据搬走。
- **每次运行都传。** `SETUP_PARAMS.dataDir` 标了 `fromProfile: true`，意味着它不接受
  每次运行的覆盖，只从配置来；`--update` 路径同样带 `--data-dir`
  （`routes/update.js:updateSetupArgs`）。`deriveDataDir()` 的顺序：配置自己的
  `dataDir` → 这套部署自己记下的值 → 空（空则上面那条拒绝逻辑生效）。
- **容器配置不参与。** 它的同一个位置由 `VolumeBinds`（`<dir>:/data`）加
  `STRATA_DATA=/data` 表达，`normalizeProfile` 里那条 `dataDir → /data` 的注释就是
  这个映射，1.1.0 已经做好了，1.1.1 只是把它和本机的字段对齐。
- **老配置保持为空，不自动迁移。** 迁移只能靠猜（`strataDir/../Strata-data`？
  `settings.json` 里的值？），而猜错正是这次要消灭的行为。用户补一次字段即可。

## 3. 每套部署一份 `settings.json`

`lib/setup-env.js`（新文件），四个导出：

| 导出 | 作用 |
|---|---|
| `setupConfigHome(strataDir)` | `<strataDir>/.config`；没有 `strataDir` 时返回 `""` |
| `setupSettingsPath(strataDir, platform)` | 上面那个目录 + `strata`（POSIX）/ `Strata`（Windows）+ `settings.json` |
| `setupConfigEnv(strataDir, platform)` | `{ XDG_CONFIG_HOME }` 或 `{ APPDATA }`；无目录时 `{}` |
| `ensureSetupSettings({ strataDir, dataDir })` | 缺失时写 `{ data_dir, installs: [strataDir] }`（与 setup 同一形状，indent 1） |

几个必须守住的细节：

- **平台分支照抄 `setup.py`，不是我们自己定的。** `setup.py:3478` 在 Windows 上读
  `%APPDATA%/Strata/settings.json`（大写 S，**完全忽略 XDG**），POSIX 上读
  `$XDG_CONFIG_HOME/strata/settings.json`（小写）。所以 Windows 上设
  `XDG_CONFIG_HOME` 等于没设。
- **只在缺失时写。** 已存在就交给 setup 维护（它每次都会重写这两个键）；我们覆盖它
  等于把它学到的东西扔掉，那个「谁最后跑谁拥有」的竞态就回来了。
- **没有 `dataDir` 就不写。** 一份没有 `data_dir` 的设置文件比没有更糟：setup 会以为
  读到了值，实际退回 `ROOT.parent / "Strata-data"`。
- **写不进去不致命。** `write-failed` 只进 setup 日志，启动链继续——只读的 Strata 目录
  不该让整个 App 起不来。
- **变量绝不泄漏到服务启动。** `withSetupConfigEnv()` 永远返回新对象：`buildEnv()` 可能
  直接返回 `process.env` 本身，就地改会让这个变量跟着进每一次 spawn，包括根本不读那份
  文件的 `serve/server.py`。
- **每次 setup 一行日志。** `describeSetupEnv()` 打出 `XDG_CONFIG_HOME=…` /
  `APPDATA=…` 与「写入 / 跳过 / 失败」，事后能回答「这次运行读的是哪份设置文件」，
  而这个问题在共享文件时代是无解的。

## 4. setup 不开浏览器

`setup.py` 的 `open_browser` 默认 true，会写进配置，并且它生成的 `run-<model>.sh` /
`.bat` 带 `--open`。对一个自己就是 UI 的 App，首启或更新时冒一个浏览器窗口纯属噪音。

- 首启：`lib/firstrun.js` 的 argv 是 `--setup --yes --no-start --no-browser`
  （注释指向 `setup.py:4610`），「运行 setup…」与新建配置都复用这条路径。
- 更新：`routes/update.js:updateSetupArgs` → `--update --yes --no-browser --data-dir …`。
- 服务启动本来就不传 `--open`，保持不变。
- **不开浏览器是固定的，不做成选项。** 用户要自己看 Strata 页面，UI 上有「打开网页」
  按钮，没有理由让后台进程去开。

## 5. 按部署收窄的进程判定

`lib/process.js` 新增三个东西，`lib/fsx.js` 补了符号链接安全的路径比较：

- `portListening(port, {host, timeoutMs})` —— 一次 TCP 握手，400 ms 超时，只问
  「有人在听吗」，不发任何请求。
- `belongsToDeployment(pid, strataDir)` —— 命令行（`/proc/<pid>/cmdline`、
  PowerShell 的 `CommandLine`）指向这套目录，或者进程 cwd 是它（覆盖
  `cd <dir> && python serve/server.py` 这类启动方式；POSIX 读 `/proc/<pid>/cwd`）。
- `listStrataPidsFor(strataDir, platform)` —— `listStrataPids()` 之后再按上面那条过滤。
  `listStrataPids()` 保留，只用于「机器上有没有任何 Strata」这类信息性判断。

`lib/deployer/source.js` 的判定顺序（`getStatus()` 第 6 步）：

1. 本部署的进程在 → `starting`；
2. 本部署没进程，但**本配置解析出的端口**有人在听 → `stopped` + `portConflict: true`；
3. 都没有 → 按配置/安装状态给 `stopped` / `no-config` …

端口解析是 `profile → 配置文件 → 8080`，不写死常量；写死的话「两套部署用不同端口」
这个唯一的隔离手段就失效了。

`start()` 遇到 `portConflict` 直接返回一句人话（端口被别的进程占着，可能是另一份
部署），不去 spawn 一个绑不上端口的服务——那样只会留下一个立刻退出的进程和一条难懂的
日志。`stop()` 只对 `listStrataPidsFor()` 的结果发信号；找不到自己的进程时返回
`already: true`（幂等，不是错误）。

**这条路径上没有任何一处会向「不属于本部署」的 pid 发信号**，这是 1.1.1 修掉的
最危险的一条。

## 6. 两个小修

- **停机也能更新。** 本地版本以前只来自运行中服务的状态，停服后显示「版本 —」，更新那
  一行塌成一个版本号——而更新流程的第一步本来就是停服。现在同时读
  `engine/BUILD.json`；本地版本未知算「无法证明是最新」，因此照样给更新入口。
- **瘦卡能切环境。** 服务停止时，`Strata 状态` 卡片上出现整页头部同款的 profile 选择器，
  选中经 `POST /profiles/select` 落库后整卡重绘；运行时换成「名字 · 类型」的只读标记。
  选项列表、运行中守卫、请求本身收进 `ui/assets/profile-picker.js`，与整页共用，两处
  不会再各写一套。平台不支持或状态里没有 profile 视图时整块不渲染。
  同一轮还修了 `versionRowPlan` 被拆模块后 `panel.js` 没 import 的问题，并补了
  `test/ui-module-imports.test.js` 这类「跨模块符号必须有 import」的静态守卫。

## 9. 明确没做的事

- **不迁移老的全局 `settings.json`。** 里面的 `data_dir` / `installs` 属于「上一套
  部署」，搬过来就等于替用户决定哪套拥有它们。
- **不给 `dataDir` 任何默认路径。** 包括看起来最合理的 `setup.py` 自己的退回值。
- **不在服务启动时注入配置主目录变量。** `serve/server.py` 不读那份文件，注入了只会
  让下一份日志看起来像「这套部署也用了它」。
- **不为容器配置做任何新事。** 容器内的 setup 由镜像承担，`/gguf` 与卷绑定由 1.1.0
  的 `docker.js` 负责。
- **不自动改老 profile 的端口。** 端口冲突只上报，让用户自己决定谁换号。
