# 1.1.0 第五批：插件配置页试点（自定义设置页）— 实现记录

对应任务：`v1.1-TASK-5.md`。本记录描述实现，权威语义以任务文件为准。

## 1. 目标形态

Hana 设置 Tab 里的 `Local Strata` 不再由宿主按 schema 平铺渲染，而是装我们
自己的 `ui/settings.html`。设置页只剩三样 + 一个入口：

```
☐ 随 Hana 启动
刷新间隔  [ 5 ] 秒
Strata API Key  [ •••••• ]      ← sensitive，真值只在后端
─────────────────────────
环境配置  → 到面板里管理
```

移到面板（profile）里的：Strata directory / Python / GPU / GGUF / Config file /
port。`profiles` / `activeProfileId` 等内部项**不显示**。

## 2. 清单

`manifest.json` 的 `contributes.settings` 同时保留 `schema` 并新增：

```json
"ui": { "route": "/settings.html" }
```

- `schema` 继续负责字段校验 / 默认值 / `sensitive` 掩码 / `profiles` 持久化。
- `ui.route` 只替换渲染；不新增第二套配置系统。

## 3. 读写通道

设置页通过 App 自己的已认证路由读写，后端再落到 `ctx.config`：

| 方法 | 路由 | 作用 |
|---|---|---|
| `GET` | `/api/apps/hanako-localstrata/routes/prefs` | 读 `autoStart` / `refreshSec` / `apiKey`（掩码）|
| `POST` | `/api/apps/hanako-localstrata/routes/prefs` | 写这三个键，走 schema 校验 |

前端用 `hana.api.fetch("prefs")`（`ui/assets/settings.js`），SDK 自动带
`appSurfaceSession`，无需自己拼地址。

- `apiKey` 只回掩码 `********`；回传掩码视为「用户没改这一格」，不覆盖已存值。
  清空输入框可显式清除。
- `refreshSec` 要求 `integer >= 1`；`autoStart` 要求 boolean；非法值 400。
- 其余键（`profiles` / `activeProfileId` / 旧扁平字段）一律不碰。

## 4. 入口

「环境配置 → 到面板管理」按钮调用 `hana.cards.open("panel")`，定位 / 激活本
App 的整页主卡；profile 的列表、新建、编辑、删除仍在面板内（沿用第四批实现）。

## 8. 「到面板管理」交互修正与实测结论（1.1.0）

### 现状与要求

设置页底部的「环境配置 → 到面板管理」按钮改用官方 API
`hana.cards.open("panel")` 打开本 App 的整页主卡（`contributes.cards` 里
`id: "panel"`）。该调用在 `ui/assets/settings.js` 的 `openPanel()` 里，按钮
在等待期间禁用，成功 / 失败都有可理解提示。

### 可用性与 `minAppVersion`

- 无 `instanceKey` 的 `hana.cards.open(cardId)` 自 **Hana 0.940.0** 起对已握手的
  自定义设置页可用（见 `APPS.md`「打开本 App 的另一张卡」）。
- 只有带第二参数 `{ instanceKey }` 才要求 `minAppVersion >= "0.1021.0"`；本入口
  不传 `instanceKey`，因此不需要 `0.1021.0`。
- 当前 `minAppVersion` 是 `1.1.0-beta`（>= 0.940.0），随 App 打包的 `ui/assets/sdk.js`
  也来自同一发行版，**无需调整 `minAppVersion`**，也无需升级 SDK。

### 弹窗是否关闭 —— 实测结论（重要）

**结论：`hana.cards.open("panel")` 会定位 / 激活面板页卡，但不会关闭承载它的宿主
设置弹窗（`settingsModal`）。**

依据（对运行中的 Hana 1.1.0-beta 产物做代码级核对）：

- `desktop/dist-renderer` 里 `hana.cards.open` 的处理器（`QK`/`KK`/`VK`/`nI`）只操作
  chalkboard 布局 store 与 `createChalkboardCardInstance` / `dispatchChalkboardLayoutCommand`。
- 设置弹窗的开 / 关由另一套 store 字段 `settingsModal.open` 控制；全产物中把它置为
  `false` 的只有 `xb()`（弹窗自己的关闭按钮 / 遮罩）与 `Qa()`（切到市场弹窗）。
- 没有「卡片激活时自动关闭设置」的订阅或副作用，也没有供 App 调用的
  「关闭设置表面」方法（`hana.*` 的 host request 白名单里没有这类请求）。

因此这不是本 App 能用官方 API 修掉的对话框问题，而是宿主侧行为：面板确实开了，
但被设置弹窗盖住，需要用户自己按关闭。

> 说明：无法在本环境里做真实 GUI 点击（没有可控的渲染进程调试通道），以上是
> 对运行中宿主产物的代码级核对，不是手工点击的目视记录。

### 方案 B：就地管理（已实现）

既然从设置表面打不开面板，就把环境配置直接搬进设置页：

- `ui/settings.html` 在三个全局偏好下方渲染 profile 列表与就地编辑器；
- `ui/assets/settings.js` 通过 `GET /profiles` 读列表，用
  `POST /profiles/save|delete|select` 新建 / 编辑 / 删除 / 选择；
- 表单按 `type` 切换字段：`local` 为 Strata 目录 / Python / 可选 GPU /
  GGUF 目录 / 端口，`container` 为镜像 / 容器名 / 数据目录 / GGUF 目录 / 端口；
- 既有规则保留：服务运行中禁用编辑与删除（后端也拒绝）、至少保留一套、
  重名与必填校验、删除走两步确认；
- `configFile` 不在本页表单里，但编辑 `local` profile 时会把原值原样送回，
  保证不丢任何已存配置。

「到面板管理」按钮及其 `hana.cards.open` 调用已移除，不再需要用户关闭设置弹窗。

### 其余备选方案（未实现，供后续选择）

1. **共用 HTML**：按 `APPS.md` 的做法，把 `contributes.settings.ui.route` 与
   `panel` 卡的 `route` 指向同一份 HTML，两边靠同一组后端路由共享配置。
   代价是面板页要同时容纳三样全局偏好与环境管理，改动会波及面板（超出
   「只改设置页」）。
2. **等宿主修复**：向 Hana 报告「从设置表面 `cards.open` 后不关闭设置弹窗」，
   由宿主在卡片激活时收起设置表面。

### 10.2 运行中实际值（来源优先级怎么落）

新增 `lib/runtime-values.js`：

- `splitCmdline` / `ggufDirFromConfig` 为纯函数；
- `localRuntimeValues({ cmdline, configJson, cfg, status })` 按
  **cmdline → 实际 config → 原始 profile → 默认值** 逐字段取第一个非空值并记
  `sources[field] ∈ runtime | profile | default`：
  - `strataDir`：cmdline 中 `serve/server.py` 的祖父目录 → runtime，否则原始
    profile.strataDir → profile；
  - `pythonPath`：紧邻 server.py 之前且含 `python` 的参数 → runtime，否则
    `status.settings.pythonResolved` → runtime，否则 profile → profile；
  - `configFile`：cmdline `--config` 的 basename → runtime，否则
    `status.configFile` → runtime，否则 profile → profile；
  - `port`：cmdline `--port` → runtime，否则实际 config.port → runtime，否则
    profile.port → profile，否则 `cfg.defaultPort` → default；
  - `gpu`：cmdline `--gpu` → runtime，否则 profile.gpu → profile；
  - `ggufDir`：`ggufDirFromConfig` → runtime，否则 profile.ggufDir → profile，
    否则 `cfg.defaultGgufDir` → default。
- `containerRuntimeValues(info, profile, cfg)` 从 `docker inspect` 取：
  `image`（Config.Image）、`containerName`（Name 去 `/`）、/data 挂载（bind →
  Source / volume → Name，volume 记 `runtime-volume`）、/gguf 挂载、`port`
  （有 published 映射时 runtime，否则 profile → default）。
- `buildRunningReport(ctx, opts)`：读 `readAllConfig` + `getStatus`；来源判定
  明确用 `cfg.profiles` 里按 `activeProfileId` 找到的**原始 profile**（不是已把
  ggufDir/port 镜像成生效值的 `cfg.activeProfile`）；不 running 时直接返回
  `running:false` 且空 `values`/`sources`，不读进程/容器。
- `routes/settings.js`：`GET /profiles/running`。

设置页只读视图新增 `#profileRuntimeNote`；`GET /profiles/running` 后，profile
为空且有运行值的输入框填入运行值（只读 disabled，不写回）并在其后插入
`.field-source` 标注（runtime / runtime-volume / default，profile 不标注）。
停止的编辑态只对空 `ggufDir`/`port` 插入 `profile.sourceDefaultValue`，**不**把
默认值写进输入框。关闭/重开编辑器调 `clearFieldSources()` 清标注并还原运行时
填充值；切语言重刷标注；读运行值失败只在提示处显示
`profile.runtimeUnavailable`，不挡抽屉。

## 11. 路径原生目录选择（1.1.0，第八批）

### 11.2 用户需要重新批准

### 12.1 镜像：本地已有就不再并排显示「拉取」

真机反馈：「镜像框选中 `strata:latest`、下面写着"本地已有此镜像"，旁边还摆着
「拉取」」——自相矛盾。现在拉取入口由一个状态机决定（`renderImageAction()`，由
`renderImageStatus()` 每次重画时一并重画，`hidden` 而不是 `disabled`）：

| 状态 | 状态行 | 拉取入口 |
|---|---|---|

「本地没有，需要下载」。

## 13. 运行中的锁按“这套是否正在使用”收窄（1.1.0，第十批）

真机反馈：只要服务在跑，**所有**配置行都变「查看」（只读），想改一套没在用的
配置也得先停服务。现在改成按“这套是否正在被使用”判定。

### 13.1 判据

- 前端（`ui/assets/settings.js` `renderProfiles()`）：`const inUse = serviceRunning
  && isActive;`
  - 行内动作：`inUse` → 文本 `profile.view` + `ICONS.eye` + 以只读打开；否则
    `profile.edit` + `ICONS.pencil` + 可编辑。
  - 删除：`del.disabled = working || inUse || profiles.length <= 1`。
  - 抽屉：`openProfileEditor(p, inUse)`；`askDeleteProfile()` 的守卫从
    `if (working || serviceRunning) return` 改为 `if (working) return` +
    `if (serviceRunning && profile.id === activeProfileId) return`。
- 后端（`routes/settings.js`）：`assertNotRunning(ctx, action)`（一律禁）换成
  `assertProfileMutable(ctx, cfg, profile, action)`：仅在
  `profile.id === cfg.activeProfileId` 时拒；文案改为
  “服务运行中，不能{修改|删除}正在使用的配置；请先停止服务”，仍含“运行中”
  子串以便前端错误映射继续生效。
- `deleteProfile` 校验顺序澄清为：配置不存在 → 运行中锁 → 至少保留一套。
  （原来运行中锁在最前面，导致“删一个不存在的 id”会报运行中。）

### 13.2 「删除」为什么一并放开（判断与理由）

**判断：运行中允许删除非使用中的配置**（使用中的仍禁，且至少留一套仍生效）。
理由：删除走的是和修改完全相同的纯配置写（`writeProfiles` →
`savePluginConfig` → `ctx.config.setMany`），没有任何服务动作；“不许动”的
原初理由（不要扰到正在跑的那套）对非使用项不成立。若只改可改、却只删不可删，
会留下一个自己都解释不通的不对称（能改不能删）。删除侧额外的安全网仍在：两步
确认、`profiles.length <= 1` 拒绝、使用中的那套拒绝。

### 13.3 边界确认

**1）运行中改非使用中的配置，不会重启/中断服务——成立。** 读代码：
`routes/settings.js` 的 `/profiles/save` / `/profiles/delete` 只调
`readAllConfig` / `validateProfile` / `writeProfiles` / `savePluginConfig` /
`getStatus`；文件里 **不 import `startService` / `stopService`**，`restartService`
全文件只有 1 处调用，在 `POST /settings`（配置文件参数编辑 + `restart:true`，
不是 profile 路径）。全仓 `index.js` / `lib/` 没有任何 `ctx.config` 变更订阅或
watcher，因此写 `profiles` / `activeProfileId` 不会触发任何生命周期动作。运行中
的服务自己持有 argv / 容器，改另一套配置影响不到它。（已加测试钉住：
`the profile routes never touch the service lifecycle`。）唯一附带写入：
local 的 `getStatus()` 在未选配置文件时会自动选定并持久化**旧扁平 `configFile`
键**（既有行为，与本轮无关，也不是服务动作）。

**2）删除：同一逻辑放开**（见 13.2）。

**3）仍假设“运行中一律禁改删”的地方（已列出，本轮**未动**）：**
`ui/assets/panel.js` 的 `renderProfileList()`：`edit.disabled = state.working ||
running`、`del.disabled = state.working || running || list.length <= 1`，且行内
按钮恒为「编辑」（没有查看/只读态）。面板也 POST `/profiles/save` /
`/profiles/delete`，所以后端放宽后面板在 API 上也能写成，但它的按钮仍硬禁，
两边不会出现可见分歧；将来若要对齐，面板应改用同一个 `inUse` 判据。

### 15.1 镜像：三态按钮的最终定义

| 状态 | 状态行 | 按钮文案 | 按钮动作 |

- 理由（用户澄清）：“重新拉取”指**同名 tag 但 registry 上内容已更新**（`latest`

  方式报错，不隐藏、不禁用。

  对可用性做任何断言（避免首帧报一个空的 `field.imageListFailed` 或误标“本地已有”）。
