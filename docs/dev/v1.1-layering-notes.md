# 哪一层的东西放哪一层（v1.1 layering notes）

这份笔记回答一个问题：**一个设置该放 profile、放全局，还是放「运行 setup…」？**
判据只有三条，**先定生效时机，再定归属**。每条结论后面都带文件:行号；标了「代码级」的是读码得出的，「未实测」的是没在真机跑过的。

场景：本地源码部署（`strata-iq3_s.json`），RTX 4060 Ti 16 GB + 91 GB RAM。

---

## 1. 统一判据（三类）

| 改了之后… | 它属于 | 放哪 |
|---|---|---|
| **下一次请求**或**下一次启动**就生效（不必重跑 setup、不必重建容器） | 环境 / 运行参数 | profile（或全局默认） |
| **必须重跑 setup** 才生效 | **setup 的输入** | 不放 profile；放面板的「运行 setup…」对话框 |
| **必须重建容器** 才生效 | 环境定义（容器的形状） | 容器 profile |

推论（本轮反复用到）：
- 「下次启动生效」也算第一类：我们每次启动都重新读 profile 拼 argv（见下表 `port`/`gpu`/`pythonPath`），所以**改 profile 就能改启动参数**。
- 只有**第二类**该从 profile 里挪走。本轮只找到 `ggufDir` 一个。

## 3. 本轮三个关键事实

### 3.1 启动**不纠正** config（代码级，未实测）

- 我们的启动 argv 只有：`[server.py, --engine, strata, --config <绝对路径>, --port <n>]`，profile 填了 GPU 才加 `--gpu`（`lib/deployer/source.js:292-293`）→ **没有任何覆盖路径的参数**（无 `--gguf-dir`/`--native`/`--pack`）。
- 引擎侧读完 config 只做一件事：把**相对**路径按 `cwd` 解析（`serve/server.py:5654` 读、`:5711` 解析），**不回写**；它读的 env 全是 `STRATA_API_KEY`（`:5631`）、`STRATA_ALLOWED_HOSTS`（`:5764`）、调试/调优开关（`:554`、`:636`、`:2216`…），**没有模型/pack 路径类**。
- 服务会写的文件只有：自己的 log（`:641`）与**兄弟文件** `.shared-settings.json`（`:2947`；`svc.config_path = a.config` 只供网页读取，`:5826`）。
- 会写 config 的只有三处，都不是启动：①「参数编辑」保存（逐键外科式改写：`routes/settings.js:304` → `lib/deployer/index.js:229`）②跑 setup（重建 `args`）③引擎自带网页的 Model settings 卡（人工点击、留 `.bak`，`docs/DETAILS.md:824-828`）。

### 3.2 apikey 有**两个角色**（代码级，未实测）

| 角色 | 谁提供 | 何时读 |
|---|---|---|
| 服务端「**要什么 key**」 | 本机：**config 的 `api_key`**（我们启动不传 `--api-key`，`source.js:292`；服务接受 `--api-key`/`$STRATA_API_KEY`/config 的 `"api_key"`，`serve/server.py:5414-5415`；校验在 `:4443-4447`）。容器：镜像 env（值来自我们的 env 文件） | 服务/容器**启动时**一次 |
| 插件「**发什么 key**」 | `resolveApiKey`：profile → 全局 `defaultApiKey` → 容器运行缓存 → config 的 `api_key`（`lib/deployer/common.js:1109-1114`） | **每次请求** |

要点：覆盖值是"我们发什么"，**不改变服务端要什么**；两者不一致会 401（语义如此，不是 bug）。
**改 config 的 `api_key` 只能靠 setup 或手改**：`setup.py:4609` 有 `--api-key`（会写进 config）；我们的 `EDIT_KEYS`（`lib/deployer/common.js:641` 起）**没有** apiKey 字段。

### 3.3 GGUF 目录为什么从 profile 移到「运行 setup…」

它是 **setup 的输入**：`setup.py:5170-5171` 用 `--gguf-dir` 决定 `models_dir`/`shards`，再写进 config 的 `args`（`:5351` 的 `--native`/`--ple-gguf`）。所以**改了不重跑 setup 完全不生效**——证据是你自己的日志：启动命令念的仍是 config 里的旧路径（`strata-iq3_s.log:6120`）。
现在的三级兜底：**对话框 → 全局默认目录 → 让 setup 下载**（`lib/firstrun.js:41` 白名单、`:105` 生效目录计算；目录存在性检查 `routes/config.js` 的 `checkGgufDir`）。

## 4. 操作建议：把模型挪到 NVMe

`--native` / `--ple-gguf`（那张每 token 要随机读的 28.8 GB 表）跟着 `--gguf-dir` 走；`--pack`(1.5 GB) / `tokenizer` / `--mtp`(787 MB) / `vision.mmproj` / `--expert-profile` **不跟**（`setup.py:5299` pack 由 data 目录决定；`:5283-5291` mmproj 先看 `<data>/models/`）。

**做法 A（走界面）**：设置页「全局」→ 默认模型目录填 NVMe 路径 → 面板停服务 → 「运行 setup…」→ 确认。
代价：**`args` 被重建** → 手调过的 `--vram-reserve-mib` 等回到 setup 的决定；`sampling` 等顶层设置会保留（carry_over，`setup.py:3658-3683`）。

**做法 B（手改 config，3 处）**：改 `args` 里的 `--native`、`--ple-gguf`，以及顶层 `vision.model`。
安全依据：pack **不含绝对路径**（只记文件名）；`--tokenizer`/`--expert-profile` 不受影响；启动/重启都不写 config（3.1）。
代价：以后**重跑 setup 会覆盖**（那是 3.3 说过的"重建 args"）→ 所以**同时**把全局默认目录留在 NVMe 路径上，让将来重跑生成同样的路径。

**收益预期**：prompt 与启动改善明显；稳态 decode 可能只有几个百分点（**推断，未实测**）。

## 技术债：布尔 flag 只能加，不能删（2026-10-17）

**事实**：`--vram-elastic`（以及 `--kv-grow`、`--no-pool` 这类无值 flag）只能**写进去**，**撤不掉**。
写入器的 `arg-add` 会"有则改写、无则追加"，而"改写"要求 `"--flag", "value"` 成对存在——无值 flag 没有值，
所以它的 presence 就是全部状态：`applyTextEdit` 为它单独加了一条分支（有则原样返回、无则追加一个裸 flag），
但**没有任何操作能把它从 args 里删掉**（`lib/deployer/common.js` 的 `insertArgPair` / `applyTextEdit`）。

**行为后果**（已按此设计，不是 bug）：
- UI 里它是**两态**下拉：「— 关（不写这个 flag）—」/「on」；
- 一份 config 里**没有**该 flag → 选 on 会追加 ✓；选「关」= 什么也不写 ✓；
- 一份 config 里**已有**该 flag → 再选「关」在 `editDiff` 里是"有值→空"，属于**清空** →
  面板按既有规则**拦下保存**（提示不支持清空）→ 也就是说：**开了就撤不回来**，只能手改 config；
- 默认关 → 打开是安全的，所以这条债的**风险面很小**，但不能不说。

**要还的时候怎么做**：给写入器加一个 `flag-remove` 操作（在 args 数组里删掉该 flag 及其可选的后续值，
字符串感知扫描，删完再 `JSON.parse` 校验），配一条测试（注入"删一个存在的裸 flag"与"删一个成对 flag"）。
在那之前，`--kv-grow` / `--no-pool` 这类**默认关**且**撤不回**的开关都不进 UI。
