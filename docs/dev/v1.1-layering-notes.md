# 哪一层的东西放哪一层（v1.1 layering notes）

这份笔记回答一个问题：**一个设置该放 profile、放全局，还是放「运行 setup…」？**
判据只有三条，**先定生效时机，再定归属**。每条结论后面都带文件:行号；标了「代码级」的是读码得出的，「未实测」的是没在真机跑过的。

场景：本地源码部署（`strata-iq3_s.json`），RTX 4060 Ti 16 GB + 91 GB RAM。

---

## 1. 统一判据（三类）

| 改了之后… | 它属于 | 放哪 |
|---|---|---|
| **下一次请求**或**下一次启动**就生效（不必重跑 setup、不必重建容器） | 环境 / 运行参数 | profile（或全局默认） |
| **必须重跑 setup** 才生效 | **setup 的输入** | 不放 profile；放面板的「运行 setup…」对话框 |
| **必须重建容器** 才生效 | 环境定义（容器的形状） | 容器 profile |

推论（本轮反复用到）：
- 「下次启动生效」也算第一类：我们每次启动都重新读 profile 拼 argv（见下表 `port`/`gpu`/`pythonPath`），所以**改 profile 就能改启动参数**。
- 只有**第二类**该从 profile 里挪走。本轮只找到 `ggufDir` 一个。

## 3. 本轮三个关键事实

### 3.1 启动**不纠正** config（代码级，未实测）

- 我们的启动 argv 只有：`[server.py, --engine, strata, --config <绝对路径>, --port <n>]`，profile 填了 GPU 才加 `--gpu`（`lib/deployer/source.js:292-293`）→ **没有任何覆盖路径的参数**（无 `--gguf-dir`/`--native`/`--pack`）。
- 引擎侧读完 config 只做一件事：把**相对**路径按 `cwd` 解析（`serve/server.py:5654` 读、`:5711` 解析），**不回写**；它读的 env 全是 `STRATA_API_KEY`（`:5631`）、`STRATA_ALLOWED_HOSTS`（`:5764`）、调试/调优开关（`:554`、`:636`、`:2216`…），**没有模型/pack 路径类**。
- 服务会写的文件只有：自己的 log（`:641`）与**兄弟文件** `.shared-settings.json`（`:2947`；`svc.config_path = a.config` 只供网页读取，`:5826`）。
- 会写 config 的只有三处，都不是启动：①「参数编辑」保存（逐键外科式改写：`routes/settings.js:304` → `lib/deployer/index.js:229`）②跑 setup（重建 `args`）③引擎自带网页的 Model settings 卡（人工点击、留 `.bak`，`docs/DETAILS.md:824-828`）。

### 3.2 apikey 有**两个角色**（代码级，未实测）

| 角色 | 谁提供 | 何时读 |
|---|---|---|
| 服务端「**要什么 key**」 | 本机：**config 的 `api_key`**（我们启动不传 `--api-key`，`source.js:292`；服务接受 `--api-key`/`$STRATA_API_KEY`/config 的 `"api_key"`，`serve/server.py:5414-5415`；校验在 `:4443-4447`）。容器：镜像 env（值来自我们的 env 文件） | 服务/容器**启动时**一次 |
| 插件「**发什么 key**」 | `resolveApiKey`：profile → 全局 `defaultApiKey` → 容器运行缓存 → config 的 `api_key`（`lib/deployer/common.js:1109-1114`） | **每次请求** |

要点：覆盖值是"我们发什么"，**不改变服务端要什么**；两者不一致会 401（语义如此，不是 bug）。
**改 config 的 `api_key` 只能靠 setup 或手改**：`setup.py:4609` 有 `--api-key`（会写进 config）；我们的 `EDIT_KEYS`（`lib/deployer/common.js:641` 起）**没有** apiKey 字段。

### 3.3 GGUF 目录为什么从 profile 移到「运行 setup…」

它是 **setup 的输入**：`setup.py:5170-5171` 用 `--gguf-dir` 决定 `models_dir`/`shards`，再写进 config 的 `args`（`:5351` 的 `--native`/`--ple-gguf`）。所以**改了不重跑 setup 完全不生效**——证据是你自己的日志：启动命令念的仍是 config 里的旧路径（`strata-iq3_s.log:6120`）。
现在的三级兜底：**对话框 → 全局默认目录 → 让 setup 下载**（`lib/firstrun.js:41` 白名单、`:105` 生效目录计算；目录存在性检查 `routes/config.js` 的 `checkGgufDir`）。

## 4. 操作建议：把模型挪到 NVMe

`--native` / `--ple-gguf`（那张每 token 要随机读的 28.8 GB 表）跟着 `--gguf-dir` 走；`--pack`(1.5 GB) / `tokenizer` / `--mtp`(787 MB) / `vision.mmproj` / `--expert-profile` **不跟**（`setup.py:5299` pack 由 data 目录决定；`:5283-5291` mmproj 先看 `<data>/models/`）。

**做法 A（走界面）**：设置页「全局」→ 默认模型目录填 NVMe 路径 → 面板停服务 → 「运行 setup…」→ 确认。
代价：**`args` 被重建** → 手调过的 `--vram-reserve-mib` 等回到 setup 的决定；`sampling` 等顶层设置会保留（carry_over，`setup.py:3658-3683`）。

**做法 B（手改 config，3 处）**：改 `args` 里的 `--native`、`--ple-gguf`，以及顶层 `vision.model`。
安全依据：pack **不含绝对路径**（只记文件名）；`--tokenizer`/`--expert-profile` 不受影响；启动/重启都不写 config（3.1）。
代价：以后**重跑 setup 会覆盖**（那是 3.3 说过的"重建 args"）→ 所以**同时**把全局默认目录留在 NVMe 路径上，让将来重跑生成同样的路径。

**收益预期**：prompt 与启动改善明显；稳态 decode 可能只有几个百分点（**推断，未实测**）。

## 技术债：布尔 flag 只能加，不能删（2026-10-17）

**事实**：`--vram-elastic`（以及 `--kv-grow`、`--no-pool` 这类无值 flag）只能**写进去**，**撤不掉**。
写入器的 `arg-add` 会"有则改写、无则追加"，而"改写"要求 `"--flag", "value"` 成对存在——无值 flag 没有值，
所以它的 presence 就是全部状态：`applyTextEdit` 为它单独加了一条分支（有则原样返回、无则追加一个裸 flag），
但**没有任何操作能把它从 args 里删掉**（`lib/deployer/common.js` 的 `insertArgPair` / `applyTextEdit`）。

**行为后果**（已按此设计，不是 bug）：
- UI 里它是**两态**下拉：「— 关（不写这个 flag）—」/「on」；
- 一份 config 里**没有**该 flag → 选 on 会追加 ✓；选「关」= 什么也不写 ✓；
- 一份 config 里**已有**该 flag → 再选「关」在 `editDiff` 里是"有值→空"，属于**清空** →
  面板按既有规则**拦下保存**（提示不支持清空）→ 也就是说：**开了就撤不回来**，只能手改 config；
- 默认关 → 打开是安全的，所以这条债的**风险面很小**，但不能不说。

**要还的时候怎么做**：给写入器加一个 `flag-remove` 操作（在 args 数组里删掉该 flag 及其可选的后续值，
字符串感知扫描，删完再 `JSON.parse` 校验），配一条测试（注入"删一个存在的裸 flag"与"删一个成对 flag"）。
在那之前，`--kv-grow` / `--no-pool` 这类**默认关**且**撤不回**的开关都不进 UI。

## 「模型目录」：一个字段，三条路径（2026-10-17）

**为什么一个字段不是一值**：一份 config 里指向模型分片的有**三处**——`--native`（分片 1）、
`--ple-gguf`（含 PLE 表的那一片；原版是最后一片，Swift 是第一片）、以及 `vision.model`
（图像编码器重复用分片 1）。只换 `--native` 会得到一个"文本换了盘、视觉还读旧盘"的配置，
所以它们必须一起动。反过来，`--pack` / `tokenizer` / `--mtp` / `--expert-profile` / `exe`
**不是分片路径**（都在数据目录下），一个都不动：换模型不是搬安装。

**为什么不是"前缀拼接"**：只把目录前缀换掉，在新目录里文件名不一致时会静默写出一条不存在的路径。
`resolveModelDirOps`（`lib/deployer/common.js`）改为**按名字找**：先找同名分片，找不到再找**同量化**
（`IQ3_S` / `UD-Q4_K_XL` / …）的分片组；分片数必须与原配置一致、每一片都得在、同量化有多个候选就报错。

**这是 setup.py 缺的那道校验**：`gguf_dir_shards`（setup.py:1420）在找不到同名文件时会拿目录里唯一的
`*-00001-of-*.gguf`（不看量化），`gguf_dir_problem`（:1465）只检查"这文件能不能跑"，于是
**一份 IQ3_S 文件被写进了 model_name 标成 IQ3_XXS 的 config**，还照它重建了一个 `packs/iq3_xxs`
（pack 的 `index.txt` 头部写着 from `…-IQ3_S-00001-of-00002.gguf`，pool 与 iq3_s 那份逐字节一致）。
面板这个字段的校验因此**比 setup 更严**：量化和段数都对不上就拒绝，不静默顶替。

**顺手修掉的写入器 bug**：`applyTextEdit` 原先用"文本变没变"当"正则匹配上没上"，
于是**把一个值写成它已经是的那个值**会被判成"配置中找不到参数"并抛错（同样的问题在 num 分支）。
改成用 `re.test(text)` 判定。这是"真默认值"与恒等重写的前提：改值与现值相同必须是合法的空操作。

**界面形态**：参数编辑里它是独立的一组「模型」（组内顺序：字段 → 现值行 → 提示），
现值用 `.field-current`（"现在读的是 X"）而不是 `.field-default`（"引擎默认：X"）：
前者回答"这份文件**现在**读什么"，后者回答"**留空**会怎样"。
只读项的 `.cf-readonly-item` 也不能用在这里：那个样式的语义是"这个值改不了"，而这个字段恰恰是改它的。

## 档位：两个内存数，两件事（2026-10-17）

**事故回顾（已实测）**：一次「运行 setup…」在 96 GB 的机器上把 IQ3_S 装成了 IQ3_XXS。
`strata-setup.log` 里两行钉死了原因：`[ok] size: IQ3_XXS`、`[ok] images: off`。前者是
`setup.py:4988` 的 `rec = "IQ3_XXS" if ram >= 60`（**只看 RAM**，且 `--yes` 直接采纳推荐）；
后者是 `setup.py:5106` 的 `ask("Do you want images?", …, "n", a.yes)`——**默认答案就是"不要"**。

**口径决策：MemTotal 干两件事，必须分开算。**

| 用途 | 用哪个数 | 为什么 |
| --- | --- | --- |
| **可行性**（这一档能不能跑） | `os.totalmem()/2**30` = **setup 的 `ram_gb()` 同一个数**（MemTotal，本机 91.15 GiB） | 只要和 setup 用同一个数，就不会出现"我们显示可选、它打印不可行"的错位。`MODELS[*].ram_gb` 是 setup 的门槛（48/60/62/32），它本来就是按 MemTotal 写的 |
| **默认推荐**（选哪一档） | **标称容量** = 把 MemTotal **向上取整到标准容量**（16/24/32/48/64/96/128/192/256…）：91.15 → **96** | `docs/MODELS.md` 的表现在按标称写（32/48/64/"96 GB 或更多"）。拿 91 去比"96"永远落进 64~96 那道缝——本次 bug 的产房 |

取整法的三个检验（都是测试里钉住的）：96 GB 条子（91 GiB）→ 96 档 ✓；真 64 GB 机器（61-63 GiB）→ 64 档，不会爬到 96 ✓；
128 GB（123 GiB）、192 GB（185 GiB）→ 仍是"96 或更多"档 ✓；`README` 里那台 AMD 机"47 GB RAM"（= 48 GB 条子，46.9 GiB）→ 48 档 ✓。
它天然容忍固件/iGPU 的预留，因为向上取整不问"少了多少"。

**过滤与推荐**（`lib/model-tiers.js`，服务端算、界面只画）：
- 可行性逐条照抄 setup 的判据：`ram >= ram_gb`；不够时看低内存模式（`low_ram_needed` + `low_ram_fits`，`setup.py:3267/3295`，
  `LOW_RAM_HEADROOM_GIB = 10`）；`budget` 档（Unsloth）**没有**低内存变体（`setup.py:4990` 无 experts.bin）；
  `nvidia_only` 在 AMD 上不可行。**我们比 setup 严**（它只会 `confirm_risk` 然后照装），方向是安全的那一边。
- 推荐按文档表：32 → Coder，48 → IQ2_XS，64 → IQ2_XS，96+ → **IQ3_S**；该档不可行时先找"正常装得下"的最好一档，
  再退到低内存模式里最省内存的一档；**Coder 只在 32 档和最后兜底**（文档原话：RAM 够就选完整模型）。
- 不可行的档**照样列出来并置灰**，标签里带原因（`需要 62 GB 内存，本机 91 GiB` / `仅 NVIDIA`）。隐藏会让人怀疑列表，
  禁用+原因能让人学到约束。

**传参**：`--family` / `--model` 都是 setup 自己的参数（`setup.py:4574-4575` 的 `choices`），进 `SETUP_PARAMS` 白名单。
两者成对传（只传 `--family` 等于点名一支却不点名档位，被 `validateSetupParams` 拒），并且**必须显式传**：
不传的话 setup 会用自己的推荐，本次事故就会重演。

**界面上还有一句真话**：`#sp-modelRam` 显示"本机可用内存 91.2 GiB（标称 96 GB）→ 按 96 GB 档推荐；
setup 自己按 91.2 GiB 判断可行性"——两个数都摆出来，档位就不再是魔法。

**顺手修掉的 ReferenceError**：`openDrawer` 里 `/profiles` 的返回值是 `const` 声明在 `try` 里，
却在 `try` 之后读（`visionInfo = data?.vision`）——**每次打开抽屉都抛**，于是 `visionInfo` 永远是 null，
「运行 setup…」的视觉预填永远落回"由 setup 决定"（= 关）。现在抽成 `loadProfileFacts()`（外层绑定 `profileData`），
抽屉和对话框都走它，对话框在填表**之前** `await` 它。`node --check` 与 G4 都抓不到这类"作用域外读变量"，
由 `test/setup-model.test.js` 的结构断言兜住形状。

## 「性能」块闪烁：显示与否绑在一个会抖的采样上（2026-10-17）

**现象**：面板每 5 秒刷新，「性能」整块一会儿消失一会儿出现。

**根因是两层，缺一不可**：

1. **渲染侧**（`ui/assets/panel.js` 的 `paint()`）：
   `els.speedBox.hidden = isSetup || !els.speedRows.children.length`。
   把"整块显示与否"绑在"这次刷新解析出了几条指标"上——样本为空就没有行，没有行就藏整块。
2. **数据侧**（`lib/deployer/source.js` 的 `readRecentLogs()`）：日志目录里有**两份同时在写**的文件：
   - `strata-iq3_s.log`：config 自己声明的 `log`，`strata serve: … read in N ms (X tok/s), … generated in N ms (Y tok/s)` 在这里；
   - `strata-strata-iq3_s.log`：引擎二进制自己写的，格式是 `[strata] done: 220 tokens in 7 s (49.2 tok/s)`，
     **`parseMetrics` 一条也匹配不到**。
   旧实现按 `listLogFiles()` 的 **mtime 倒序**取第一个。两份文件在**同一个请求**里先后追加，
   mtime 相差一两秒且轮流当"最新"——于是数据源每几秒就换一次：读到引擎日志的那轮，四个字段全空，
   渲染侧就把整块藏了；下一轮又读到服务器日志，块又出现。**闪烁频率 = 刷新频率**，因为根因就长在每次刷新上。

**实测证据**（2026-10-17 01:0x，用户部署正在跑）：`strata-iq3_s.log` 646 KB / 1375 条匹配 / mtime `00:03:30`；
`strata-strata-iq3_s.log` 63 KB / **0** 条匹配 / mtime `00:03:44`（更新）。修前按 mtime 会读到后者（0 指标），
修后直接读 config 声明的那份：`tg 43.9 / pp 432.2 / expert 70.1 / kv 99.57`。
同一个原因也解释了"日志区展开全是 —"：`#logsBox` 走的是同一个 `readRecentLogs`。

**修法**：
- 数据侧：`readRecentLogs` 先读 **config 声明的 `log`**（`declaredLogPath()`），读不到才退回"最新的那份"。
- 渲染侧：显隐改成**服务状态**（`running || starting/stopping/restarting`），并且 `paintSpeeds()` 永远渲染
  同样的四行，没测到就写 `—`。这样"有数/没数"只改变单元格，不改变布局，也不改变可见性。

**测试**：`test/performance-block.test.js`（5 项）——旧条件不许再出现、四行恒定、`metrics` 永不省略（`EMPTY_METRICS` 形状）、
以及一条用夹具复现 mtime 竞争的用例（引擎日志更新 → 仍必须读声明的那份）。

**顺带发现**：`test/config-routes.test.js` 里 8 条"停止态"用例依赖真实机器——服务在跑时守卫会正确地拒绝，
用例就会红。现在这些用例在检测到本机有 Strata 进程时 `t.skip`（守卫在工作，不是回归）。

## 并发（`parallel`）：参数归属、显存分档、以及"不会崩"的依据（2026-10-18）

### 它是什么

`parallel: N` 是**顶层 config 键**（不是 args），语义是"同时解码 N 条会话"。**默认 1 = 一次一个**，其余请求
在服务端排队。`--batch` / `--slots` 是引擎侧同一件事的别名；`--parallel` 只是 setup 的旁路参数（引擎不认它）。
setup 只在 `--parallel >= 2` 时写这个键（`setup.py:5489-5497`），不传则 **carry over**（我们的字段因此不会被一次
setup 重跑冲掉）。

**它是真并发，但不是"轮流跑完"**：`docs/BATCHING.md:3` 的原话是每个 verify window 里"carries one token of
each conversation"，权重每个窗口只读一次——所以每请求 tok/s 下降（实测 −9%~−24%）、总吞吐上升、没人需要等别人
的整段回答。服务端证据：`slot_q` 每槽一条输出流（`server.py:725`）、`BT`/`BDONE` 按槽投递（`:766`）、
`pick_slot` 按"已持有的前缀"分配（`:1424-1447`）、prompt-cache 复用要求**完全相同的前缀** —— 因此不会把 A 的
KV 当成 B 的。

> `serve/server.py:7` 那句 "One sequence at a time behind a FIFO" 是**上游的**过时注释（2026-09-24 写下，
> batch 在 2026-10-04 才进 `server.py`），按约定**不改上游**；我们自己的文档不引用它作结论。

### 代价从哪来（我们曾经判反过）

- `docs/BATCHING.md:56`：每个槽占的显存是"the expert cache would otherwise hold"的——**从专家缓存让出来**，
  不是额外索取。引擎自己的日志也这么说：`the expert cache (N slots) gives the K/V room below slot X`。
  所以后果是**缓存变小 → 命中率略降 → 每请求变慢**，不是 OOM。
- `--kv-resident 32768` 的方向是**相反的**：把整段 KV 挪进 pinned RAM、显存只留 32K 窗口，于是"more experts
  fit on the GPU"（`docs/DETAILS.md:79`，引擎 help："the freed VRAM goes to expert slots"）。
- 单槽显存 = `min(ctx,32768 if streaming else ctx) × 12×(576|1056)/1e9 + 0.17`（`setup.py:4283-4287`）≈ 0.59 GiB；
  整段 KV 在内存 ≈ 13.7 KB/token（`DETAILS.md:82`）→ 256K ≈ 3.6 GB/槽。
- `parallel_recommend`（`setup.py:4290-4305`）判的是**值不值得推荐**（缓存仍要装得下模型专家的一半、
  槽最多占缓存 20%），**不是装不装得下**；引擎对任何 N 都"honoured as asked"，装不下就少开槽。

### 分档是本 App 的产品规则（`ui/assets/parallel-tier.js`）

| 总显存（MiB） | 开关 | 推荐 | 上限 |
|---|---|---|---|
| ≤ 8192 | 禁用（有原因文案） | — | — |
| ≤ 12288 | 可开，标注不推荐 | 2 | 2 |
| ≤ 16384 | 可开 | 2 | 3 |
| ≤ 24576 | 可开 | 3 | 4 |
| ≤ 32768 | 可开 | 4 | 6 |
| > 32768 | 可开 | 4 | 8（引擎窗口） |

- **用 MiB 比较**：16 GB 卡实测报 16380 MiB，用 GiB 去比 `> 16` 会把它顶进 24 GB 档。
- **用总显存**：分档是"这张卡多大"，可用显存每次请求都在变，用它会让推荐值来回跳。
- 读不到显存（服务停着 / 没有 nvidia-smi）→ **不禁用**，按 16 GB 档保守处理并写明——偶发的读取失败不该
  变成永久的功能缺失，而真实成本在确认框里已经讲清。
- 服务端只校验 `1..8`（1 = 关），**按档上限由界面守**；手工构造请求可越过档位上限，但仍受引擎 8 槽窗口约束。

### 写入路径：`top-key`

`parallel` 是唯一可编辑的顶层键，所以需要一条与"逐键改 args"不同的写入口（`setTopLevelValue`）：
**深度校验**（该词只要出现在嵌套层就拒绝）→ **同名唯一** → 原位改写/末尾插入（沿用文件缩进）/删除（前吃或后吃逗号）→
**`JSON.parse` 复核 + 顶层键集合逐个比对**。值 1 表示"引擎默认"，所以**删键**而不是写 1；因此"开→关"能回到
原始字节（测试钉住了这一点）。
